# TenkoCall 中心運用 + HCE 分割セッション計画

Refs: [ippoan/sesame#1](https://github.com/ippoan/sesame/issues/1)（結論コメント 2026-07-12）

関連: `plan/nfc-universal-unit-st25r3916-note.md`（HCE + Custom Protocol の下回り検証）、
`plan/nfc-android-hce-verification.md`（既存 PCSC リーダーでの HCE 読取検証）、

## 方針（sesame#1 結論）

当面の目標は **alc-app + alc-app-s3 + TenkoCall の3構成での運用**とする。

| コンポーネント | 役割 |
|---|---|
| **alc-app** | Web フロントエンド / バックエンド連携（既存） |
| **alc-app-s3** | CoreS3 ハブ（FC-1200 RS232C・BLE 機器の集約） |
| **TenkoCall** | キオスク以外のすべて: **顔認証・点呼機能・車検証読み取り・免許証読み取り** |
| **AlcoholChecker** | **予備（フォールバック）**。運用上はキオスク（kiosk）役に限定 |

SESAME Face 静脈認証（キオスク側フォールバック生体認証）は予備扱い・保留
（sesame#1 参照。2026年8月末予定の CANDY HOUSE 公式 ESP32 SDK 更新後に再評価）。

## 点呼フロー（HCE 分割セッション）

```
TenkoCall (スマホ)                     キオスク (AlcoholChecker / CoreS3)
─────────────────                     ─────────────────────────────
① 顔認証 + 点呼開始
② 車検証・免許証読み取り (必要時)
③ HCE タッチ① ──────────────────────▶ 測定引き継ぎ
   (点呼セッショントークンを渡す)        │
                                       ▼
                                      FC-1200 アルコール測定
                                       │ 測定結果は rust-alc-api へ
                                       │ トークン紐付きで保存
④ HCE タッチ② ◀─────────────────────┘
   (測定完了確認・結果参照)
⑤ 点呼継続・完結 (TenkoCall 内)
```

- キオスクへ引き継ぐのは**アルコール測定だけ**。本人確認（顔認証）・点呼記録の主体は TenkoCall
- タッチ①とタッチ②は**別セッション**（測定中はスマホをリーダーから離す前提）。
  同一点呼への復帰は点呼セッショントークンで行う

### 設計課題（要検討）

- [ ] **点呼セッショントークン設計**: ワンタイムトークン + 署名 + 短期失効。
      `ippoan/rust-alc-api#480` / `ippoan/alc-app#72` の device pairing (RFC 8628 スタイル)
      実装パターンの流用可否を確認（リプレイ攻撃対策を含む）
- [ ] **測定結果の返却経路の選定**（3案）:
  - **案A: サーバー経由**（タッチ②は「完了通知」のみ、結果は rust-alc-api から取得）
    → キオスク→スマホ方向の CE ハード不要。**推奨・まずこれで設計**
  - 案B: タッチ②で HCE 応答に結果を同梱（キオスク側リーダーがチャレンジ提示）
    → 既存 PCSC リーダーで可（スマホ側 HCE が応答するだけ）
  - 案C: キオスク側 CE（M5 NFC Unit / ST25R3916）でスマホが読み取る
    → 新規ハード必要。`nfc-universal-unit-st25r3916-note.md` の「キオスク発信」フロー
- [ ] タッチ①→測定→タッチ②の**タイムアウト設計**（測定放棄・別人割り込みの排除）
- [ ] キオスク側の同時利用（複数ドライバーの点呼セッションが並ぶ場合）の排他制御

## TenkoCall 側の実装項目

### 顔認証

- [ ] alc-app（web/）の human.js 実装（`useFaceAuth` / `face-db`）の Android 移植方針を決定
      （WebView 再利用 or ネイティブ ML Kit / TensorFlow Lite）
- [ ] 顔テンプレートの保存先（端末ローカル vs rust-alc-api）と、
      **個人スマホでのなりすまし対策**（他人端末での認証・登録顔差し替えの防止）

### 点呼機能

- [ ] 点呼記録の項目定義（改善基準告示・点呼規程との整合）
- [ ] rust-alc-api 側の点呼セッション API / スキーマ設計（measurements との紐付け）

### 免許証読み取り（運転免許証 IC）

- [ ] ISO14443 Type-B。読み取りに**暗証番号1/2**が必要 → PIN 入力 UX、
      3回誤りロックの警告表示
- [ ] 読み取り項目の選定（氏名・免許証番号・有効期限・免許の条件等）
- [ ] 読取失敗時のフォールバック（券面 OCR or 手入力）
- [ ] rust-alc-api 側スキーマ拡張（employees への免許情報紐付け・有効期限アラート）

### 車検証読み取り（電子車検証）

- [ ] 2023年1月以降の電子車検証は ISO14443 Type-B + **セキュリティコード**（券面記載4桁）
- [ ] 国交省「車検証閲覧アプリ」相当の読み取りを自前実装するか、
      閲覧アプリ連携（共有インテント等）で済ませるかを判断
- [ ] rust-alc-api 側スキーマ拡張（車両マスタ・車検有効期限アラート）

## 規制面の再確認（キオスク顔認証 → スマホ顔認証への変更に伴う）

`cores3-hub-consolidation.md` の規制検討は**キオスク側顔認証**を前提に書かれている。
本方針では本人確認が個人スマホ側に移るため、以下を再確認する:

- [ ] 遠隔点呼（告示第5条）「生体認証符号等により確実に識別する機能」を
      **個人スマホの顔認証**で満たせるか（端末・アプリの真正性担保を含む）
- [ ] 「全身+検知器使用状況の随時確認カメラ」要件は引き続き既存の監視カメラ運用
      （ippoan/alc-app#27 の ONVIF 死活監視）で満たす前提を維持
- [ ] 識別（TenkoCall 顔認証）と測定（キオスク FC-1200）が**別デバイス・時間差**になるため、
      なりすまし・混入の余地がないこと（HCE トークンによる時間結合で担保）の整理

## 既存 plan との関係・差し替え

- `cores3-hub-consolidation.md` の「顔認証（タブレット側カメラ）→ QR → 測定」フローは
  **本方針で差し替え**。QR は `nfc-universal-unit-st25r3916-note.md` で
  スクリーンショット複製リスクにより不採用済みであり、連携は HCE に統一する
- AlcoholChecker（Device Owner Kiosk）は kiosk 専任・予備扱いに役割縮小。
  凍結する機能（NFC 社員カード読取・キオスク側顔認証等）の棚卸しは別途実施
- `nfc-android-hce-verification.md` の「既存 PCSC リーダーで SELECT AID→レスポンス往復」検証は、
  本方針の**クリティカルパス**に格上げ（タッチ①の成立確認そのもの）
